# KB System 生产部署指南

> **所有人上线生产都按这份来。** 2026-09-24 起生效,取代之前「拉 ghcr 镜像」的流程。
> 有疑问或流程要改,先改这份文档再改 workflow,不要口头约定。

---

## 1. 一句话流程

```
本地改代码 → push main → 手动触发 Deploy PROD → 盯到绿 → 打开 kb.sharewb.cloud 验证
```

生产只有一条上线路径:**GitHub Actions 的 `Deploy PROD` workflow**。
不 rsync 手工上传、不 SSH 上去手工 build、不在服务器上改代码。

## 2. 环境速查

| 项 | 值 |
|---|---|
| 服务器 | 腾讯云南京 `175.27.231.228`,用户 `ubuntu`,docker 需 `sudo`(免密) |
| SSH | `ssh -i ~/.ssh/id_rsa_github_deploy ubuntu@175.27.231.228`(key 找负责人要) |
| 对外域名 | **kb.sharewb.cloud**(主系统)/ skillhub.sharewb.cloud / aihub.sharewb.cloud |
| 不可用域名 | `*.tokenwave.cloud` —— 未备案,腾讯云拦截,别再往代码/文档里写 |
| 运行目录 | `/opt/kb-system`(compose / .env / 证书挂载 / 运行时状态) |
| 构建目录 | `/opt/kb-build`(CI 同步过来的源码,**只读,别手改**) |
| 镜像 | 只在本机:`kb-backend` / `kb-frontend-prod` / `kb-edge`,tag 有 `:latest`(当前)、`:prev`(上一版)、`:sha-xxxxxxx` |

为什么在服务器上 build:服务器在国内,连不上 github.com,从 ghcr.io 拉镜像只有 ~76KB/s(backend 镜像要拉几个小时)。
所以改成 CI 只把**源码增量** rsync 过去,服务器用腾讯云内网 apt / PyPI / npm 源自己 build。

## 3. 标准部署步骤

### 3.1 部署前(本地)

```bash
# 前端改动:类型检查必须过
cd frontend && npx tsc --noEmit -p tsconfig.json

# 后端改动:至少能 import
cd backend && python -c "import main"
```

然后 commit + push 到 main。

### 3.2 确认 push 已经到远端

```bash
git fetch origin && git log --oneline -1 origin/main    # 必须是你刚 push 的那个 commit
```

> 历史教训:push 还没完成就触发部署,会把 push 之前的版本部署上去。

### 3.3 确认没有别的部署在跑

```bash
gh run list --workflow deploy-prod.yml --limit 3
```

有 `in_progress` / `queued` 的,**等它结束**,或者找触发人沟通。workflow 已加并发锁(同一时间只跑一个),但排队的旧 run 跑起来仍会覆盖你的版本。

### 3.4 触发

```bash
gh workflow run deploy-prod.yml --ref main -f confirm=deploy
# 需要强制全量重建(backend+frontend+edge):
gh workflow run deploy-prod.yml --ref main -f confirm=deploy -f force_all=yes
```

也可以在 GitHub 网页 Actions → Deploy PROD → Run workflow,`confirm` 填 `deploy`。

### 3.5 盯进度

```bash
gh run list --workflow deploy-prod.yml --limit 1          # 拿 run id,确认 headSha 是你的 commit
gh run watch <run-id> --exit-status
```

各阶段和正常耗时:

| Job / Step | 做什么 | 正常耗时 |
|---|---|---|
| Detect changed services | 对比上次成功部署(`prod-live` tag),决定建哪些服务 | 秒级 |
| Run Tests | 后端测试(只在后端有改动时跑) | ~1 min |
| Frontend tsc + build | 前端类型检查 + 构建(只在前端有改动时跑) | ~1.5 min |
| Sync source to server | rsync 源码增量到 `/opt/kb-build` | 通常 < 1 min |
| Build & deploy on server | 服务器 build → 切换 → 健康检查 → celery 优雅重启 | 3-10 min;celery 有长任务时最多再等 30 min |

**build 阶段线上完全不受影响**(还是旧版本在跑),只有切换那几十秒会出维护页。

### 3.6 部署后验证

1. 打开 https://kb.sharewb.cloud ,登录,点开你改的功能实际用一遍
2. 前端改动:页面右下角会提示「有新版本」,或看 `https://kb.sharewb.cloud/version.json` 的 sha
3. 服务器上核对镜像(可选):
   ```bash
   ssh ... 'sudo docker ps --format "{{.Names}} {{.Image}} {{.Status}}" | grep kb-system'
   ```
   本次部署的服务应显示 `kb-xxx:sha-<你的 commit 前 7 位>`
4. 对外可感知的新功能:写一条 changelog(见团队约定)

## 4. 禁止事项(每一条都出过事)

| 不要做 | 为什么 |
|---|---|
| **重跑(Re-run)很久以前失败的 Deploy PROD** | 重跑用的是**当时那个 commit 的 workflow 和代码**,会把旧版本(甚至旧 edge 配置)部署上去。要部署就重新 `gh workflow run` |
| 两个人同时触发部署 | 两个 run 抢同一台机器,互相覆盖 |
| SSH 上去手工 `docker compose build` / `up --build` | 绕过测试和版本记录,下次 CI 部署会把你的改动覆盖掉 |
| 在服务器上直接改代码 / nginx 配置 | 同上。紧急热修也必须**当天回写仓库**(见 §6.3) |
| 手动改 `/opt/kb-build` 里的文件 | 下次 rsync `--delete` 会覆盖;而且会让 build 结果和仓库对不上 |
| `docker image prune -a` / `docker system prune -a` | 会删掉 `:prev` 回滚镜像和 python/node 基础镜像。清理用 `docker image prune -f`(只删悬空镜像) |
| 往代码里写 `tokenwave.cloud` 域名 | 在腾讯云被拦截,写了就是坏链接。对外地址用 `sharewb.cloud`,内部调用走内网(见 §7) |

---

## 5. 失败了怎么办

先看是哪一步挂的:`gh run view <run-id>`,再 `gh run view <run-id> --log-failed`(网络不稳时可能 EOF,多试一次)。

| 挂在哪 | 线上受影响吗 | 处理 |
|---|---|---|
| Run Tests / Frontend tsc | 否 | 修代码重新 push + 部署 |
| Sync source to server,报 `i/o timeout` / `Connection refused` | 否 | 服务器 IP 变了或 SSH 不通。先本地 `ssh` 试;IP 变了要改 GitHub Secrets `DEPLOY_HOST`/`DEPLOY_USER` |
| Build & deploy,输出「❌ xxx build 失败,线上未改动」 | 否 | 看日志里的报错。常见:依赖包在腾讯源里没有 / 版本号写错 / Dockerfile 语法 |
| 「❌ 新 edge 配置 nginx -t 不通过」 | 否 | edge 配置有错,本地修好再部署 |
| 「❌ Health check failed」 | 短暂 | **已自动回滚到 `:prev`**。看日志里的 backend logs 找原因 |
| 「❌ edge 健康检查失败」 | **是,全站** | edge 不自动回滚,立刻按 §6.2 手动回滚 edge |
| celery_worker 那步超时 | 否(站点已上新版) | 在跑的长任务没 drain 完。SSH 上去看 `docker ps` 里 worker 的镜像,必要时手动 `up -d --no-deps celery_worker` |

## 6. 手工操作(只在紧急情况下,做完在群里说一声)

所有命令都在服务器 `/opt/kb-system` 目录下执行。

### 6.1 回滚 backend / frontend 到上一版

```bash
cd /opt/kb-system
# backend(celery_worker 用同一个镜像,一起回)
sudo BACKEND_IMAGE=kb-backend:prev docker compose up -d --no-deps backend celery_worker
sudo docker exec kb-system-frontend-1 nginx -s reload     # backend 换了 IP,前端 nginx 要重新解析
# frontend
sudo FRONTEND_IMAGE=kb-frontend-prod:prev docker compose up -d --no-deps frontend
```

回滚后,**把 main 上的问题 commit revert 掉再正常部署一次**,否则下次部署又会带上。

### 6.2 回滚 edge(全站入口)

```bash
cd /opt/kb-system
sudo EDGE_IMAGE=kb-edge:prev docker compose up -d --no-deps edge
curl -fsS http://127.0.0.1/health && echo edge-ok
```

### 6.3 紧急热修后回写仓库

如果不得不在服务器上改了文件,当天必须:
1. 把改动原样提交到仓库(服务器上的文件 → 本地 → commit → push)
2. 正常走一次 Deploy PROD,确认 CI 构建出来的版本包含你的修改

> 历史教训:2026-09 迁移时 edge 的 sharewb 配置只改在服务器上,差点被 CI 用仓库里的旧配置覆盖,全站下线。

### 6.4 查日志 / 进数据库

```bash
sudo docker logs -f --since 30m kb-system-backend-1
sudo docker logs -f --since 30m kb-system-celery_worker-1
sudo docker exec -it kb-system-postgres-1 psql -U kb_admin -d kb_system
```

### 6.5 数据库迁移

workflow 不跑迁移。需要时部署完手动执行:

```bash
sudo docker exec kb-system-backend-1 python -m scripts.<迁移脚本> --dry-run   # 先 dry-run
sudo docker exec kb-system-backend-1 python -m scripts.<迁移脚本>
```

## 7. 服务器专属配置(不在仓库里,重装会丢)

| 文件 | 作用 |
|---|---|
| `/opt/kb-system/.env` | 所有密钥和环境变量。改完 `docker compose up -d --no-deps <服务>` 生效 |
| `/opt/kb-system/docker-compose.override.yml` | 新机专属:skillhub 前端挂自定义 nginx(`newserver/skillhub-frontend.conf`) |
| `/etc/letsencrypt/live/*.sharewb.cloud` | 证书。root crontab `17 3 * * * scripts/renew-sharewb-ssl.sh` 自动续期 |
| `/etc/docker/daemon.json` | Docker Hub 镜像加速(腾讯云 mirror) |
| 数据库 `agent_configs` 的模型 `api_base` | 指向内网 `http://10.206.0.11:8080/v1`(aihub),不走公网域名 |

服务间互相调用(kb → aihub、skillhub → aihub)一律走内网 `10.206.0.11`,不要走公网域名。

## 8. 其它服务

### 8.1 Skill Hub(独立仓库 zhebinliu/skillhub,不走这条 workflow)

代码在服务器 `/opt/kb-system/skillhub/`(普通目录)。改完推到 skillhub 仓库后:

```bash
# 本地把改动文件传上去(示例:main.py)
scp -i ~/.ssh/id_rsa_github_deploy backend/main.py ubuntu@175.27.231.228:/tmp/
# 服务器上
cd /opt/kb-system
sudo docker tag kb-skillhub-backend:latest kb-skillhub-backend:prev    # 先留回滚点
sudo cp /tmp/main.py skillhub/backend/
cd skillhub/backend && sudo docker build -f Dockerfile.cn -t kb-skillhub-backend:latest .
cd /opt/kb-system && sudo docker compose up -d --no-deps skillhub-backend
```

对外地址由 `.env` 的 `SKILLHUB_PUBLIC_URL` 决定(当前 `https://skillhub.sharewb.cloud`)。

### 8.2 AI Hub(new-api / aihub-tap)

独立 compose:`/opt/new-api`、`/opt/aihub-tap`,不随 kb 部署变化。
